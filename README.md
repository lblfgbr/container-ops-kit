# Ops Studio — AI 驱动的研发质量治理与容器运维工作台

> 将 UT 治理、MR 检视与合入、质量检查和构建部署组织成可执行、可验证、可追踪的工作流程。

Ops Studio（[GitHub 仓库 `lblfgbr/ops-studio`](https://github.com/lblfgbr/ops-studio)）面向研发人员、代码检视人员和版本质量负责人，将 Pi Agent 与 CodeHub、WeLink、质量数据源、SSH、Kubernetes 和 Helm 连接起来，覆盖从质量问题发现、测试修复、代码检视到合入跟踪，以及构建、产物对比和环境部署的日常工作。

项目重点解决 AI 进入真实研发流程后的三个问题：**如何把分散操作串成持续推进的任务，如何用测试与远端状态验证执行结果，如何让人工判断和经验进入后续自动化过程。** AI 负责需要理解代码与上下文的修复和检视，平台负责流程编排、结果校验和状态留存，人在关键节点确认质量、处理异常。

## 场景与问题

在多版本、多仓库并行交付中，UT 失败、覆盖率不足、MR 待检视和环境部署往往需要同时推进。相关信息分布在质量报表、代码仓、问题单、群消息和远程环境中，研发人员除了处理问题本身，还需要反复查询状态、传递信息和衔接流程。

| 面向角色 | 典型工作 | 主要痛点 |
| --- | --- | --- |
| 研发人员 | 修复失败 UT、补充测试、提交代码并跟进 MR | 从报表定位到仓库后，仍需准备分支、复现失败、修复、回归、建单和提交；一次修复之后还要持续跟进流水线与检视意见 |
| 代码检视与审核人员 | 接收群内 MR、检查改动、确认意见闭环并审核合入 | MR 链接散落在群消息中；新提交需要复检，旧意见需要核对，流水线、权限和人工结论需要反复确认 |
| 版本与质量负责人 | 汇总多版本质量问题、推进治理、查看成果 | 报告查询、异常筛选和任务跟进分散；难以区分“AI 已执行”“测试已通过”和“代码已合入” |
| 构建与环境维护人员 | 远程构建、比较产物、修改配置、部署和查看资源 | 操作依赖命令与个人经验，涉及不同环境和多个服务；产物差异、配置确认与执行日志缺少统一入口 |

这些工作的共同难点是：单个动作可以脚本化，但跨工具流程仍依赖人工衔接；AI 可以给出建议或修改代码，但实际执行效果还需要工程证据确认。

## 方案与能力

平台以“自动化空间”和“容器运维”承载两类工作，通过工具中心、全局概览和应用中心提供统一入口。自动化概览遵循“先看成果，再处理需要关注的任务”，将已形成的治理成果与待人工处理事项放在同一工作视角中。

| 工作场景 | 当前能力 | 形成的结果 |
| --- | --- | --- |
| UT 治理 | 获取质量报告、筛选待治理仓库，执行基线测试，修复失败用例或补充测试，定向验证与全量回归，关联问题单并创建 MR，跟踪后续流程 | 测试执行证据、修复及新增用例记录、问题单与 MR 关联、治理状态 |
| MR 检视 | 手动输入 MR 链接或从配置的 WeLink 群接收 MR，执行 AI 检视与增量复检，读取远端检视意见，检查流水线与门禁，衔接人工审核和 CodeHub 检视、审核、合入 | 当前提交对应的检视结果、意见状态、人工结论、远端合入状态；手动任务仅私信授权账号 |
| 质量检查 | 按版本、团队查询 UT、接口测试和静态检查，筛选异常并导出 CSV | 可追踪的查询任务、异常清单和后续治理输入 |
| 构建与部署 | 环境连接测试与架构探测，单分支构建、双分支构建与产物对比，按服务下载产物，Chart 配置分析、审阅与部署 | 构建产物、文件差异、部署配置、分阶段日志与历史记录 |
| 容器资源管理 | 查询 Kubernetes / Helm 资源，预览和执行支持的资源操作 | 与所选环境关联的资源视图和操作入口 |
| 审核经验复用 | 记录人工审核理由，按仓库整理适用经验，支持编辑、停用和冲突确认，供后续检视使用 | 带来源、适用条件与修订号的服务知识 |

上述场景共享工作台，但各自保留独立的任务与门禁。虚机运维目前为预留入口，应用中心提供外部工具入口管理。

## 核心设计与创新

### 1. 将质量报表转化为可推进的治理任务

UT 治理从报告中的失败用例与覆盖率问题出发，连接仓库准备、基线执行、Agent 修复或补测、测试验证和 MR 流程。平台根据实际测试结果区分失败修复与测试补充，避免只凭历史报表决定当前工作。

修复过程中，将上一轮失败证据交给 Agent 继续处理；提交后，继续跟踪当前提交的流水线与检视状态。流程遇到无法确认的结果时保留任务现场和日志，转为人工处理，让自动化任务具有明确的起点、推进条件和停止条件。

### 2. 用测试证据验证 AI 修复成果

Java UT 治理要求 Agent 仅修改仓库或子模块 `src/test/` 下的测试文件；JavaScript UT 治理仅允许修改 `website/` 内符合测试命名或测试目录规则的 Jest 测试文件及测试 mock。禁止修改生产代码、删除或禁用测试、弱化断言；JavaScript 治理还禁止修改包配置、锁文件、Jest/Babel 配置和已有快照。平台结合文件差异检查、禁止标记检查、测试及断言数量检查，对常见违规改动进行拦截，再执行测试验证；这些检查为质量约束提供支撑，仍需结合代码检视判断测试语义是否合理。

平台解析实际 UT 执行报告，对比基线与回归中的用例标识：

- **修复用例**：基线失败、回归执行通过的用例。
- **新增用例**：基线中不存在、回归执行通过的用例。
- **回归门禁**：命令成功、实际执行了测试、无失败或错误，原有用例未丢失、跳过数未增加，原有成功和失败用例均执行通过。

因此，“生成了测试代码”“测试执行通过”“MR 已创建”和“MR 已合入”分别记录。新增用例数也不等同于覆盖率提升幅度，覆盖率变化仍需通过后续质量报告验证。

### 3. 将群协作转化为提交级的 MR 工作流

平台从日常 WeLink 群协作中接收 MR 链接，在既有沟通方式上增加自动检视、状态跟踪和处理回执。首次检视读取当前 MR 改动；再次提交时，基于上次成功检视的提交进行增量复检，并复核历史意见；无法取得可靠增量时回退全量检视。

检视后通过 CodeHub CLI 重新读取远端意见，以实际未闭环意见决定能否继续。检视结果、人工审核和流水线检查均关联当前提交 SHA；提交变化时，原结果不能直接用于新提交。执行审核、合并等动作时继续检查权限和门禁，并核对远端结果，减少重复操作与状态误判。

### 4. 将人工判断沉淀为可复用的审核经验

群监听的标准 MR 检视流程默认启用人工审核，可按配置关闭；手动发起的 MR 始终保留人工审核。人工审核支持记录通过、不通过及原因，列表提供一键审核与批量操作，详情保留完整判断入口。关闭群监听流程的平台人工审核后，仍需通过 CodeHub 权限和合并门禁。

人工理由可结合当前改动和历史审核记录整理为仓库级知识，保留来源和适用条件。无冲突的新经验可进入后续检视上下文；与既有知识冲突或需要改写既有结论的内容进入待确认状态，避免自动覆盖已经形成的规则。知识编辑采用修订号校验，并支持停用，使经验复用保留人工修正入口。

### 5. 以确定性流程承接 AI 判断与远程执行

平台将代码理解交给 Agent，将可明确校验的操作交给程序：质量数据按固定规则解析，构建按配置步骤执行，部署从环境与产物信息补全 Chart，在审阅模式下经人工确认后执行，任务状态和日志持续保存。

长任务采用队列与并发限制；构建等流程通过 SSE 展示过程。SQLite 统一保存业务状态。服务重启后，中断的构建和部署标记为失败，执行中的 UT 治理任务转为待人工处理；MR 中可继续跟踪的等待状态仍会轮询远端。写操作结果不确定时先核对状态，不自动重放已中断或待核对的写操作，让故障处理有可追查的依据。

### 6. 复用平台能力，逐步扩大适用范围

环境配置、任务记录、日志、连接设置和工具入口集中管理，后端按环境、构建、部署、UT、质量检查与 MR 等业务模块组织。新增版本、仓库、团队或环境时，可以复用已有配置与流程；新增业务场景仍需实现对应模块及其门禁。

应用中心支持配置外部 HTTP/HTTPS 工具入口，降低日常入口分散带来的切换成本，也为平台后续扩展保留统一的访问位置。

## 典型工作流变化

| 场景 | 人工处理方式 | Ops Studio 的处理方式 | 人工关注点 |
| --- | --- | --- | --- |
| UT 失败治理 | 查报告、拉代码、复现、修复、回归、建单、提 MR，再逐项跟进 | 报告发现问题后进入治理流程，Agent 按失败证据修复，平台验证并跟踪 MR | 业务断言合理性、复杂异常及最终交付质量 |
| UT 测试补充 | 阅读代码与覆盖率报告，逐个编写和执行测试 | 针对待治理仓库补充测试，定向验证后执行回归，记录实际新增通过用例 | 测试场景有效性与后续覆盖率变化 |
| 群组 MR 协作 | 从群里找链接，逐个检视、查意见、查流水线、找人审核与合入 | 接收 MR 后推进检视与检查，集中呈现人工待办，按权限衔接审核合入 | 业务判断、AI 漏检或误报、异常门禁 |
| 多版本质量检查 | 分别查询版本与检查项，再手工整理异常 | 按版本和团队查询、筛选异常、保存结果并导出 | 异常优先级、责任协调与治理效果 |
| 构建与部署 | 登录远程环境，执行命令、找包、比较文件、修改配置并部署 | 统一管理任务、产物与差异，按服务确认配置并执行部署 | 环境选择、配置差异和部署结果 |

## 项目价值与成效衡量

### 业务价值

- **减少流程衔接成本**：将报告查询、测试执行、MR 跟踪和群回执连接起来，减少重复查询、信息搬运与人工盯守。
- **提升质量过程的可检查性**：用基线与回归报告核验测试成果，以当前提交的远端意见、流水线和门禁状态约束 MR 推进。
- **缩短协作反馈路径**：将分散的待审核、待修复和异常任务集中呈现，使人员更快定位需要判断的事项。
- **积累可复用的工程经验**：将人工审核理由转化为带来源和适用条件的服务知识，供后续检视参考和修正。
- **支持持续推广**：以配置和模块化能力复用多版本、多仓库、多环境的治理与运维流程，逐步扩大自动化覆盖范围。

适用于多仓库、多版本并行研发中的 Java / JavaScript UT 治理、团队 MR 协作、版本质量检查和 Kubernetes 环境构建部署。

### 已具备的成效记录能力

| 衡量方向 | 可使用的记录或指标 | 解释边界 |
| --- | --- | --- |
| UT 治理产出 | 修复用例数、新增通过用例数、修复及补测服务数 | 来自基线与回归结果对比；不能直接等同于已合入成果或覆盖率提升 |
| MR 交付情况 | 处理 MR、已合入 MR、待处理与异常记录 | 按仓库和 MR 标识去重，区分重复检视次数与 MR 数量 |
| 人工协作成本 | 人工介入次数、审核次数、审核等待中位数与 P90 | 等待时长体现流程延迟，不能直接视为人工投入工时 |
| 检视质量反馈 | 人工标记的 AI 漏检、误报、不通过原因 | 反映已记录的反馈；未经完整样本核验不能称为检视准确率 |
| 知识复用 | 有效知识条数、知识使用记录 | 使用次数体现引用情况，不代表已证明的质量收益 |
| 构建部署过程 | 执行状态、阶段日志、产物与差异记录 | 任务完成时长与人工操作时长应分开统计 |

## 技术实现与使用说明

前端采用原生 HTML / JavaScript 与 Vite，后端采用 TypeScript / Fastify，业务状态存储于 SQLite。一个 Node.js 后端进程统一提供业务 API、编排任务并写入 SQLite；只读目录扫描使用独立 Worker，Git、Pi 等外部工具由后端启动。平台后端不依赖 Java、Maven 或 Spring Boot，Java UT 治理仍需目标项目要求的 JDK / Maven 环境；JS UT 治理需要目标项目的 JDK / Maven 初始化环境、Node.js / npm 及项目依赖仓库访问权限。

不同能力按需准备 Pi Agent、CodeHub CLI、WeLink CLI / MCP、质量数据源及远程环境访问条件。相关身份认证和操作权限由对应工具与目标系统校验。

项目内置 Skill 保存在 `skills/`，随项目代码更新，当前包含完整的 `code-review-skill`。平台启动 Pi 时统一加载该目录中的 Skill；同名时项目版本优先，个人目录及 Pi 原有资源发现继续保留。Windows 个人目录通过当前用户主目录解析为 `%USERPROFILE%\.agents\skills`，不需要修改用户名或复制文件。明确指定 `--no-skills` 的知识整理等任务不注入 Skill。新增项目 Skill 时放入 `skills/<名称>/SKILL.md`，配套指南、脚本放在该 Skill 目录内；下次启动 Pi 生效。该加载规则只作用于平台启动的 Pi，不修改本机全局配置。

## 启动

项目包名为 `ops-studio`，前端包名为 `ops-studio-frontend`。

需要 Node.js 22.22.3+（22.x）或 24.15+（24.x）和 npm，支持 npm 10.9.8。Windows 双击 `start.bat`，脚本会按锁文件安装依赖、迁移检测到的 H2 数据、编译后端，然后启动：

- TypeScript 后端：监听 `127.0.0.1:8080`。
- Vite 前端：监听 `0.0.0.0:5173`，启动成功后自动打开本机入口 `http://127.0.0.1:5173`。

项目支持局域网访问：其他电脑使用 `http://<运行 Ops Studio 的电脑的局域网 IP>:5173` 打开页面，前提是网络连通且主机防火墙允许访问该端口。页面的 `/api` 请求由 Vite 转发到运行机器的 `http://localhost:8080` 后端，因此后端监听回环地址不影响通过前端进行局域网访问。

手动启动：

```bash
npm ci
npm run migrate
npm run build
npm start
```

另开终端启动前端，使用与 Windows 脚本一致的局域网监听方式：

```bash
npm ci --prefix frontend
npm run dev --prefix frontend -- --host 0.0.0.0 --port 5173 --strictPort
```

如仅需本机访问，将前端启动参数中的 `--host 0.0.0.0` 改为 `--host 127.0.0.1`。`--strictPort` 保证端口被占用时明确失败，不会自动切换到其他端口。

## 页面入口

正式应用以 `frontend/index.html` 为页面源，通过上述 Vite 命令启动，调用真实后端 API；生产构建输出到 `frontend/dist/`。根目录的 `npm start` 只启动后端 API，不托管前端页面或 `frontend/dist/`。

根目录 `mock-demo.html` 是独立的 mock 交互演示和页面方案确认稿，可以直接双击打开，或单独分享这一个文件，用于演示和重构分析。样式、脚本和示例数据均已内嵌，无需启动后端；页面显示“离线交互演示 · 模拟数据 · 刷新重置”。模拟操作只改变当前页面内存中的数据，刷新后重置，不连接真实环境或提交真实业务操作。

页面相关修改遵循“先演示、后实现”：先修改根目录 `mock-demo.html`，提供可交互的页面方案；用户明确确认后，再将方案实现到 `frontend/index.html`、`frontend/src/` 等正式代码，并完成测试。确认前不修改正式页面源码，也不先改正式代码再生成演示。具体开发约束见根目录 `AGENTS.md`。

`npm run demo` 可从正式源码首次生成演示，需要先安装根目录和前端依赖；已有 `mock-demo.html` 时命令会拒绝覆盖，以保留页面确认稿。用户已确认的方案完成正式实现，且演示中没有待确认或尚未同步的修改后，才使用 `npm run demo -- --overwrite` 同步演示。可复用的示例数据维护在 `frontend/prototypes/current-project-mock.js`。生成演示不属于正式启动和构建流程。

首页为工具中心（`#/home/tools`），全局概览（`#/home/overview`）只汇总已保存的任务和环境状态。自动化、容器运维支持直接访问各页面地址；虚机运维保持预留状态。

应用中心（`#/applications`）可创建、编辑和删除 HTTP/HTTPS 工具入口，填写地址、功能说明并关联工作空间。应用配置保存在现有 SQLite 中，全平台共享；收藏仅保存在当前浏览器。站内打开使用 iframe，目标网站不允许嵌入时可选择新标签页打开。后端不会代理访问目标网站，也不增加账号或权限体系。

部署页的“历史任务”可查看任务并单条或批量删除。仅允许删除已成功或已失败且执行已结束的记录；删除不会卸载 Helm、修改集群资源或删除构建产物。批量操作逐条确认结果，失败不会自动重试。

## 结构

- `backend-ts/src/modules/environment`：环境配置和 SSH 连接测试
- `backend-ts/src/modules/build`：远程构建、产物与可重放 SSE
- `backend-ts/src/modules/containerresource`：Kubernetes/Helm 资源发现、预览和变更
- `backend-ts/src/modules/deployment`：Chart 补全、审阅、渲染和串行部署
- `backend-ts/src/modules/autout`：CSV 扫描、Agent 修复、测试门禁和 CodeHub MR
- `backend-ts/src/modules/automation`：群组 MR 检视、人工审核、服务知识、执行记录与成效统计
- `backend-ts/src/modules/quality`：UT、接口测试与静态检查查询、异常筛选和 CSV 导出
- `backend-ts/src/modules/applications`：应用中心外部工具入口
- `backend-ts/src/platform`：SQLite、独立 Worker和通用只读任务
- `shared`：前后端共享的数据约定
- `frontend/index.html` 与 `frontend/src/`：正式 HTML / JavaScript 页面及交互样式
- `frontend`：Vite 构建、前端测试与 mock 演示生成脚本
- 根目录 `mock-demo.html`：可直接打开的独立 mock 交互演示及页面方案确认稿，不参与正式应用启动和构建

SQLite 默认写入 `data/platform/tasks.sqlite`。数据库使用进程独占锁，不能同时启动两个使用该数据库的后端。应用支持本机及局域网访问，后端没有按浏览器 `Origin` 限制为本机来源。应用没有多用户认证，应在可信网络中使用，不能直接暴露到公网。

- `startup/startup.log`：依赖安装、数据迁移和编译
- `backend/process.log`：Node.js 后端进程启动输出
- `backend/backend.jsonl`：Fastify 请求与服务异常，JSON Lines 格式
- `frontend/frontend.log`：Vite 前端进程输出
- `platform/{taskId}.jsonl`：通用平台任务事件
- `build/{taskId}.jsonl`：构建步骤和远程命令输出
- `deployment/{taskId}.jsonl`：分析、编辑、渲染和部署输出
- `automation/group-mr-monitor.jsonl`：群组 MR 监听轮询、过滤数量、命令状态和错误（不记录群消息正文）；页面“群组 MR 检视 → 监听日志”展示最近 100 条
- `auto-ut/{taskId}.jsonl`：Auto-UT 阶段与实时事件
- `auto-ut/details/{taskId}/*.log`：Git、Maven、npm/Jest、Agent 和 CodeHub 命令的完整输出

JSON 日志会按敏感字段名脱敏。诊断时优先发送对应任务 ID 的日志文件，不要发送包含环境密码的 `data/platform/tasks.sqlite`。

H2 数据迁移由 `scripts/migrate-legacy-h2.mjs` 提供；构建、部署和 Auto-UT 的实际执行约束以对应模块的校验逻辑为准。

### JavaScript UT 治理

JS / JavaScript 报告可独立启动治理；同仓库的 Java、JS 使用独立任务。创建任务时，修复分支命名为 `<基础分支>_<账号>_<问题单号>`，不添加语言后缀，工作目录为 `<工作根目录>/<版本>/<仓库名>`；已保存任务使用其记录的实际分支名和工作目录，保留修复现场，同一目录需依次治理。Python 等其他语言显示暂不支持自动修复。

克隆后先在 `website` 执行 `mvn clean install` 初始化项目，再检查生成的 `package.json`。`scripts.test` 需使用已支持的 Jest 执行入口（直接调用、npm 脚本别名，或 react-scripts / react-app-rewired test）。其他测试框架需接入相应结果解析，不能直接套用 Jest 参数。Windows 下平台通过 Git for Windows 的 Git Bash 登录 shell 执行，登录初始化后显式切换到仓库的 `website`，再运行 Maven 或 npm；基线、修复验证和全量回归使用同一规则。自动查找 PATH 附近与常见安装位置的 Git Bash；自定义安装可设置 `AUTO_UT_GIT_BASH=C:\Program Files\Git\bin\bash.exe` 后重启。找不到 Git Bash 时明确报错，不回退到 cmd、PowerShell 或 WSL。Linux 保持原生执行。日志记录实际 bash 路径、完整参数及 shell 内工作目录。

在 `website` 内依次执行：

```sh
mvn clean install
npm run test -- --watch=false --watchAll=false --ci --runInBand --json --outputFile=<任务日志目录>/jest-results.json
```

Maven 初始化完成后直接运行 npm 测试，不额外执行 npm install。基线、修复验证、完整回归和 MR 流水线修复均读取本轮 Jest 报告；依赖缺失、套件加载失败、无有效用例和超时会阻断，不当作可修复的用例失败。Maven 初始化失败时停止，不继续执行 npm；Maven 成功后仍缺少 package.json 或 test 脚本时明确报错。后续修复和回归只运行 npm 测试，不重复 clean 初始化。

JS 初始化和基线测试前后会记录整个仓库内的文件指纹（包括 deployment 等目录中的生成文件）：未被修改的初始化配置、源码及测试文件留在工作区，不纳入治理提交；Agent 后续修改或删除初始化配置/源码仍会阻断。未跟踪的 node_modules、build、dist、coverage 产物不纳入提交，已跟踪文件仍受检查。初始化前存在未记录的修改时保留现场并停止；任务缺少初始化快照时不能事后把当前修改当作可信基线，需要在保留现场后用干净工作区重新治理。

仅允许提交 website 中的测试与 mock 文件，支持 `.test.js`、`.test.jsx`、`.spec.js`、`__tests__` 等测试路径；禁止修改生产源码、配置、锁文件和已有快照。原用例必须保留并通过，不能靠跳过测试达成成功。覆盖率仍以质量报告为准。

### UT 问题排查日志

日志默认位于 `data/logs/auto-ut/details/<任务ID>/`，设置 `PLATFORM_LOG_DIR` 时以该目录替代 `data/logs`。Java / JS 共用命令诊断：

- `diagnostics.jsonl`：任务、语言、阶段、轮次、工作目录、命令参数、开始/结束时间、耗时、退出码、超时/中断、日志文件名；JS 另记报告解析结果与阻断原因。
- `<操作名称>-<唯一ID>.log`：每次 Git、npm、Maven、Agent 命令的完整逐行输出，带时间及 stdout/stderr 来源；重试不会覆盖上一轮，文件不受内存输出摘要长度限制。
- `jest-results-<唯一ID>.json`：每轮 Jest 报告独立留档，包括测试数量、具体失败用例及堆栈。当前轮报告缺失或无法归档会记录原因状态。

日志会遮蔽常见凭据字段、认证头、URL 密码及环境中的密钥值，不记录完整环境变量或命令标准输入。遇到问题请提供任务 ID 和对应任务日志目录。主动删除任务并清理目录会一并删除该任务详细日志，请先留存；MR 合入后的自动仓库清理保留日志。

### MR 检视：手动提交与群组监听

在“MR 检视”页面输入单个 CodeHub MR 链接，点击“开始检视”即可创建手动任务，无需开启群监听或填写群 ID，也不受群监听的仓库前缀限制。通知接收人使用提交时配置的授权账号；Agent 检视完成（有意见、无意见或等待流水线）及执行异常通过现有 WeLink 私信通知，任务后续继续、审核、合入均不发送群回执。通知失败会记录状态，不自动重发，也不覆盖检视结果。

手动任务始终保留人工审核，不受群监听的关闭人工审核开关影响。重复提交执行中的手动 MR 会定位已有任务；同一 MR 正由群任务执行或存在待核对写入时，不会再次启动 Agent。误删的当前待核对记录会在重新提交时恢复显示，确认远端状态后可继续处理。记录保留“手动触发”来源，继续使用现有待处理、代码与意见、审核及执行历史能力。

`POST /api/automation/group-mr/submit` 接收 `{ "url": "https://codehub-y.huawei.com/<仓库路径>/merge_requests/<编号>" }`，返回 `{ "entryId": "<记录 ID>", "duplicate": false }`；重复提交已有执行任务时 `duplicate` 为 `true`。仅接受固定 CodeHub 域名下的合法单条 MR 链接，访问与写入权限沿用 CodeHub CLI 当前登录账号。

群组 MR 检视保持现有监听、统计、审核与合入流程。列表支持每页 10 / 20 / 50 条、仓库 / MR 搜索、阶段过滤；批量操作只作用于当前页。新到达的 MR 提示后由用户刷新加入，正在查看的列表顺序不会随轮询跳动。原 MR 的新处理记录会在原位置替换旧记录。

详情内展开「代码变更」后收起 MR 列表，左侧选择文件、右侧查看 diff；支持按当前过滤结果连续查看上一条 / 下一条，返回时恢复页码、选择和列表滚动位置。草稿保存在本次页面会话中，切换时可以保留、放弃或继续编辑；刷新整个浏览器页面会丢失草稿。

「刷新代码与意见」通过已配置的 `codehub-cli mr changes`、`mr review list` 读取当前提交和完整讨论。可定位意见所在文件、查看回复、填写关闭依据并执行 `mr review resolve`。关闭依据保存在本项目处理记录；关闭结果必须在远端再次读取确认。关闭意见不会直接审核或合并 MR，可点击「继续原检视流程」重新进入原有 Agent / 流水线 / 人工审核 / 合并门禁流程。

diff 的折叠区支持向上 / 向下展开 20 行，也可「展开全部」查看完整文件，再切回「仅看差异」。首次展开通过 `codehub-cli repo file get --ref <SHA>` 按当前提交读取文本，显式请求 content、path/file_path 及编码/大小/截断标记（含 is_limited），校验变更内容后补齐上下文；切换文件保留展开状态，提交变化后重新读取。CodeHub 省略 diff 时可按 MR 比较基线和当前提交重建文本差异；二进制、非 UTF-8、超过 4 MiB 或展开后超过 50000 行的文件会给出具体提示。MR 详情顶部常驻「一键审核」，沿用列表的直接通过逻辑及原有门禁；处理记录中仍保留通过 / 不通过选项。

代码与意见接口（均只作用于已存在的 MR 记录）：

- `GET /api/automation/group-mr/records/:id/workspace`：返回当前 SHA、文件 diff、完整讨论、写入能力和待核对状态。
- `GET /api/automation/group-mr/records/:id/file-context?sha=...&path=...`：只读当前 MR 变更文件，返回校验后的完整 diff；读取前后核对 SHA。
- `POST /api/automation/group-mr/records/:id/workspace`：`resolve` / `reply` / `create`。请求携带 SHA、唯一 `operationId`；回复和关闭还携带讨论指纹，关闭需要明确确认及依据。新增意见只接受当前 diff 中的新增行。
- `POST /api/automation/group-mr/records/:id/continue-review`：携带当前 SHA，按原任务策略继续流程。

回复 / 新增行意见需运行机器的 CLI 帮助明确支持下列适配器签名和参数才启用：`mr review reply <iid> <discussion-id> -p <project> --body <body>`、`mr review create <iid> -p <project> --body <body> --path <path> --line <line>`。程序只调用固定命令探测 `--help`；未识别的版本显示能力不足并禁用对应写入。当前开发环境没有内网 CLI，以上签名为受检测保护的适配器契约，仍需在目标网络核对实际版本；不宣称已完成真实 CodeHub 联调。

读写使用同一 MR 并发锁，写前检查 SHA 和讨论指纹；成功后回读确认。操作编号及未确认写入保存在 SQLite，重复请求不会重复执行。超时、权限异常、回读失败均保留待核对状态；刷新只读取远端，发现已生效的操作后解除拦截，不会自动重放。分页不完整、截断及缺失字段不作为已关闭或已检视依据。整个变更读取通过 CLI 完成，不会将远端文件路径用于本地文件系统写入。

### MR 大文件差异

- 变更目录首次打开默认全部展开，手动折叠状态继续保留。
- CodeHub 省略、折叠或限制单文件 diff 时，可点击“读取文件差异”，按 MR 的固定 base/head SHA 读取原文并重建；重命名使用旧路径，新增/删除读取存在的一侧。总 diff 超出命令输出限制时，重新读取不含 patch 的文件列表，再按文件加载。
- 文本读取上限为单侧 4 MiB、50000 行，展开后的差异最多 50000 行；二进制、非 UTF-8、缺失比较基线和截断响应提供具体错误。重建差异暂只读，保留已有意见展示，新增行评论仍需远端原始 diff 校验。
- 重建依赖运行环境中的 Git；真实 CodeHub CLI 与 Windows 环境仍需目标网络验证。

### MR 阶段与停止原因

当前阶段保留 Agent 检视、流水线、审核等实际步骤。普通检查异常归为检查失败，有待核对写操作时归为待处理并保留写入拦截；只有服务停止、重启时未完成的执行归为执行中断。正在执行的写操作不显示为中断，旧记录被替代也不再制造中断事件。正常等待流水线的状态跨重启保留，重启不凭空增加“需核对远端”写操作标记。历史记录保留原始原因，不自动重放外部操作。

### 批量合入按序执行

页面批量合入按确认列表顺序逐条执行，等待前一条完整处理返回后再发起下一条。明确返回未合入时记录原因并继续；请求异常、结果未知时停止后续项并标记“尚未执行”，不自动重试。批量一键审核保持原有行为。

人工一键审核会实时核对当前提交、未关闭检视意见、流水线及质量/冲突门禁。已停止任务的 Agent 意见结果待核对标记，在上述检查全部通过后可由这次人工审核解除，无需先重跑 Agent；其它未确认写操作仍需核对。审核失败后会刷新当前打开的代码与意见，提交变化不会阻止查看最新讨论，也不会把旧提交的审核自动应用于新提交。

待处理 MR 每分钟核对远端状态（后台监听暂停或浏览器关闭仍生效），已合入/关闭自动归档至执行历史；状态查询同步标题，MR 详情显示最新标题。

- MR 一键审核和手动合入共用按提交保存的远端核验结果：无未关闭意见且当前提交流水线通过才开放，核验失败、缺失或超过 90 秒则禁用；每分钟监控刷新，实际操作前再次实时核验。意见查询跳过 CLI 缓存，`resolved: null` 不再视为已关闭，不完整列表不再当作空列表；普通讨论在意见页保留显示。详情与列表同步核验状态，手动合入不会自动关闭新增意见。

### 一键审核响应与独立操作

一键审核通过 `POST /api/automation/group-mr/records/:id/review-jobs` 提交后台任务。返回 `202` 仅表示已受理，页面先显示等待核验；远端当前提交、检视意见、流水线和门禁核验通过后，才保存人工审核结论并继续检视、审核与合入。原 `human-review` 接口保留原有行为。

操作状态按 MR 保存，处理一条记录时仍可查看其他 MR、翻页或返回列表。同一 MR 的重复写操作受互斥保护；关闭提示或离开页面不会取消已受理任务。批量合入仍按确认顺序逐条执行，异常结果不自动重试。

页面通过 `GET /api/automation/group-mr/status` 读取本地任务状态，有任务执行时每 3 秒更新，空闲时每 10 秒更新；状态读取本身不触发 CodeHub 核验。后台定期核验独立运行，并为人工操作保留执行容量。阶段内复用已核验结果，减少重复 CLI 查询，关键写入前后仍检查当前提交和远端结果。

任务受理和执行结果保存在 SQLite。服务重启不自动重放未完成的审核或合入；未确认的写入继续保留核对标记。开发测试使用模拟 CodeHub 响应验证并发、门禁和调用次数，真实 CodeHub、WeLink 与 Windows 环境需在目标网络验证。
